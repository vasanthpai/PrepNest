Most teams start with one step: merge, deploy, and users see the change. That makes every deploy
risky, because **deploying the code** and **releasing the feature** are the same event.

Feature flags split them into two decisions.

## Two different things

| Deploy                             | Release                           |
| ---------------------------------- | --------------------------------- |
| New code is running on the servers | Users can see and use the feature |
| A technical event                  | A product decision                |
| Should be boring and frequent      | Should be deliberate              |

With a flag, unfinished work can be merged and deployed every day while staying invisible. When
it's ready, you turn it on: first where you test, then for everyone. If something goes wrong, you
turn it off again, with no new deploy and no code revert.

## Flags as code

Hosted flag services can switch features instantly and target groups of users. For a small team,
a typed file in the repository is often enough. Here's the idea, simplified from PrepNest's own
`src/config/features.ts`:

```ts
type AppEnv = "local" | "staging" | "production";

export const FEATURE_FLAGS = {
  blog: { local: true, staging: true, production: false },
  quizzes: { local: true, staging: false, production: false },
} as const satisfies Record<string, Record<AppEnv, boolean>>;

export function isFeatureEnabled(flag: keyof typeof FEATURE_FLAGS, env: AppEnv): boolean {
  return FEATURE_FLAGS[flag][env];
}
```

Two things the type system gives you for free:

- A misspelled flag name doesn't compile.
- Forgetting an environment for a flag doesn't compile either.

Changing a flag is a pull request: reviewed, tested by CI, and recorded in history.

## Make the release order a rule

One mistake is easy to make: switching a feature on in production that nobody tested on staging.
So make it a test:

```ts
it("never enables a flag in production unless it is enabled in staging", () => {
  const skippedStaging = Object.entries(FEATURE_FLAGS)
    .filter(([, envs]) => envs.production && !envs.staging)
    .map(([flag]) => flag);
  expect(skippedStaging).toEqual([]);
});
```

Now the release process isn't something people have to remember; CI enforces it.

## Rollback becomes a ladder

With flags, you have options before the big red button:

1. **Turn the flag off** for the broken feature. Everything else keeps the new release.
2. **Redeploy the previous version** if the whole release is broken.
3. **Platform rollback** (for example `wrangler rollback` on Cloudflare) when even CI is unavailable.

## Keep flags short-lived

Every flag is a branch in your code. Once a feature is on everywhere and stable, delete the flag
and the old code path. A flag that's been `true` everywhere for months is just clutter that makes
the code harder to read.

## Summary

- Deploy often, release deliberately.
- Flags as code are typed, reviewed and free.
- Enforce "staging before production" with a test.
- Remove flags once a feature is fully released.
