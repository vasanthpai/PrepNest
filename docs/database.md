# Database

Postgres on Neon, queried with Drizzle ORM. Why: [ADR 0012](decisions/0012-neon-postgres-and-drizzle.md).
Connection strings and branches per environment: [environments.md](environments.md#database-neon).

## Tables

| Table            | Defined in                        | Purpose                                                   |
| ---------------- | --------------------------------- | --------------------------------------------------------- |
| `users`          | `src/features/users/schema.ts`    | Signed-in people, keyed by Clerk user id                  |
| `webhook_events` | `src/features/webhooks/schema.ts` | Each received webhook, so retries are processed only once |

```
users                                   webhook_events
─────────────────────────────           ─────────────────────────────
id            uuid  PK (random)         source        text  ┐ PK
clerk_user_id text  UNIQUE NOT NULL     id            text  ┘
email         text  NOT NULL            type          text  NOT NULL
name          text                      received_at   timestamptz NOT NULL
image_url     text                      processed_at  timestamptz (null = not finished)
created_at    timestamptz NOT NULL
updated_at    timestamptz NOT NULL
```

Conventions: `snake_case` columns, `uuid` primary keys generated by Postgres, every timestamp
`with time zone`, money as integer paise ([ADR 0003](decisions/0003-money-as-integer-paise.md)).

## Code layout

| File                            | What it is                                                       |
| ------------------------------- | ---------------------------------------------------------------- |
| `src/features/<name>/schema.ts` | Drizzle tables for that feature                                  |
| `src/features/<name>/repo.ts`   | Queries only; every function takes a `Database` as its first arg |
| `src/lib/db/schema.ts`          | Re-exports every table (read by `createDb` and drizzle-kit)      |
| `src/lib/db/client.ts`          | `createDb(url)`: Neon over HTTP; the `Database` type             |
| `src/lib/db/testing.ts`         | `createTestDb()`: in-memory PGlite with the real migrations      |
| `drizzle/`                      | Generated SQL migrations + drizzle-kit snapshots (committed)     |
| `drizzle.config.ts`             | drizzle-kit settings                                             |

Pages never import a repo directly: page → service → repo (`src/features/README.md`).

## Commands

| Command               | What it does                                                             |
| --------------------- | ------------------------------------------------------------------------ |
| `npm run db:generate` | Compare the schema with the last migration and write a new SQL migration |
| `npm run db:check`    | Check the migration files are consistent (CI runs this from step 4)      |
| `npm run db:migrate`  | Apply pending migrations to `DATABASE_URL` (locally: your `dev` branch)  |
| `npm run db:ping`     | Check `DATABASE_URL` reaches the database                                |

`db:migrate` records what it applied in `drizzle.__drizzle_migrations` and skips those next time,
so running it twice is safe.

## Changing the schema

1. Edit the table in its feature's `schema.ts` (new table: also export it from `src/lib/db/schema.ts`).
2. `npm run db:generate -- --name short_description` and **read the generated SQL**.
3. Make it backward-compatible: the previous release must still work against the new schema,
   because migrations run before the new code goes live and because previews share staging's
   database ([release process §8](release-process.md#8-safe-database-migrations-expand-then-contract)).
   For example, add a column as nullable or with a default; never rename or drop in one step.
4. `npm test` (the repository tests apply every migration to a fresh PGlite database).
5. `npm run db:migrate` to update your `dev` branch.
6. Commit the schema change and the generated files in `drizzle/` together.

**Never edit a migration after it's merged**: staging and production have already recorded it as
applied. Fix forward with a new migration.

## Testing

Repository tests use `createTestDb()`: real Postgres (PGlite) in memory, created fresh for each
test, with the same migrations production gets. No database server or secret is needed, so they run
the same on every machine and in CI. A test database starts in well under a second.
